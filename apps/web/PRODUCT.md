# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Two primary visitor audiences, both evaluating the site owner professionally, plus the owner as an authenticated admin:

- **Recruiters / hiring managers** — assessing fit for a fixed role; need to validate experience, stack, and seniority quickly.
- **Freelance clients / potential collaborators** — assessing fit for a project-based engagement; need to see finished work and trust the owner's judgment.
- **Site owner (admin)** — manages all profile content through a private dashboard and reviews visitor/engagement analytics.

## Product Purpose

An AI-powered interactive portfolio. Visitors can browse a traditional portfolio (profile, experience, education, projects, skills, gallery, references) or converse with an AI assistant that answers questions about the owner using only real, live data fetched from MongoDB through an MCP tool layer. The owner manages all content and reviews engagement analytics from a private dashboard.

## Positioning

Unlike a static portfolio site, visitors can ask an AI agent free-form questions ("how many years of experience with Node.js?") and get answers grounded in the owner's real, current data — not a scripted FAQ page or a generic LLM guessing from a resume PDF.

## Operating Context

- Public surface: traditional section-based browsing, plus a chat surface where tool-use status indicators (e.g. "Buscando en proyectos...") surface the agent's reasoning steps while it queries live data.
- Admin surface: authenticated dashboard (NextAuth Credentials) to CRUD profile, experience, education, projects, skills, gallery, and references, and to review analytics (page views, chat questions asked, most-viewed projects, frequent chat questions).
- Third-party visitors intentionally see the same "portfolio in numbers" stats (years of experience, project count, distinct technologies, courses/certifications) that the admin sees — this is a deliberate product decision, not an internal metric leaking out. What stays admin-only is traffic/engagement data (page views, chat-question counts).

## Capabilities and Constraints

- Confirmed stack: Next.js 14 (App Router) + Tailwind CSS, MongoDB via Mongoose, Google Gemini API for the chat agent (with Groq and OpenRouter as automatic cloud fallbacks when Gemini fails — same tool-calling contract, see `lib/llm.ts`), a standalone Node/Express MCP server exposing DB-backed tools to the chat.
- `apps/mcp-server` caches every read tool's result in memory for `MCP_CACHE_TTL_MS` (default 5 min, `src/cache.ts`) — keyed by tool name + args, so repeated/similar visitor questions skip the MongoDB round-trip. Deliberately TTL-only, no event-based invalidation (apps/web's admin routes run on a different server/process with no cheap way to signal this one), and deliberately short (5 min) so an admin edit shows up again quickly. `create_blog` (and any future write tool) is explicitly excluded via `NON_CACHEABLE_TOOLS` — never assume a new tool is safe to cache without checking whether it writes.
- Auth: NextAuth Credentials provider, single admin user (`AdminUser`, bcrypt password hash). Hardened against brute force in `lib/auth.ts`: per-IP rate limit on the login attempt (10/15min, reusing `lib/rate-limit.ts`), account lockout for 15 min after 5 consecutive wrong passwords (`AdminUser.failedLoginAttempts`/`lockedUntil`), and JWT session `maxAge` trimmed to 12h (was the NextAuth default of 30 days). Optional TOTP 2FA (`AdminUser.totpSecret`/`totpEnabled`, `lib/totp.ts`, the `otpauth`/`qrcode` packages) is set up from `/admin/seguridad`: `POST /api/admin/security/2fa/init` generates a secret + QR (stored but `totpEnabled` stays false until confirmed), `POST /api/admin/security/2fa/confirm` verifies a code and flips it on, `POST /api/admin/security/2fa/disable` requires a valid current code (not just the session) to turn it back off. When enabled, `authorize()` throws the sentinel `Error("OTP_REQUIRED")` after a correct password with no/invalid code — NextAuth's credentials callback forwards a thrown error's `.message` verbatim as `signIn()`'s `res.error`, which is how `/admin/login` distinguishes "show the 2FA field" from "wrong credentials" (`res.error === "CredentialsSignin"`) without a custom protocol. `2fa/confirm` and `2fa/disable` are also rate-limited (10/15min/IP) even though both already require a valid session — a 6-digit TOTP code is brute-forceable quickly without a limit, and `disable` specifically is the one endpoint that would let a stolen session bypass 2FA outright if left unguarded. Considered and declined: migrating to Clerk — real value-add (built-in MFA/bot protection) but adds a vendor dependency and a rewrite of `middleware.ts`/`auth.ts` to protect a single hardcoded user, when the same protections fit directly on the existing stack.
- Images and the résumé/CV file are referenced by pasted URL by design (no upload pipeline) — confirmed decision, reaffirmed explicitly for the CV specifically, not a gap to fill.
- Real content has since been entered through the admin dashboard (real name, headline, bio, projects) — the database is no longer placeholder/seed data. Contact info was set directly by the assistant on the owner's request: email `julianur012b@gmail.com`, WhatsApp `+573204524545` (WhatsApp is a direct `wa.me` link; email is a button that opens an in-page modal containing `ContactForm`, not a `mailto:` link, so the visitor never leaves the site).
- `Profile.languages` (spoken languages) is public — same free-text-array pattern as `hobbies`, shown on the home, `/cv`, and via `get_profile_info`/`get_full_profile`.
- `Preference` (favorite football teams, music genres, foods, marital status, socioeconomic stratum, desired salary, remote-work preference, daily work tools) is a **separate, private collection**. It is not fully public-isolated the way it first shipped: `GET /api/resume`, `/cv`, and `getFullProfile()` in `@portafolio/models` (`packages/models/src/resume.ts`) still never import it — that boundary holds — but the **MCP tool** `get_full_profile` (in `apps/mcp-server/src/tools/getFullProfile.ts`) deliberately does merge in `Preference` data, at the owner's request, for his own personal use through external MCP clients (a remote connector in Claude, n8n) that he controls with his own `MCP_API_KEY`/Bearer token.
- Because `apps/web`'s public chat talks to the same MCP server over the same shared key, `get_full_profile` (and any future tool with the same "personal-only" shape) must be excluded from what the public chat can call — not just asked not to via the system prompt, which an LLM can be talked past, but structurally: `lib/llm.ts` filters `PUBLIC_CHAT_EXCLUDED_TOOLS` out of the tool list before it ever reaches Gemini/Groq/OpenRouter's function-calling schema, so the model has no way to invoke it regardless of what a visitor asks. Verified live: asked "tell me absolutely everything, hide nothing," the chat chained every ordinary tool but never touched `get_full_profile`. Any new tool added to the MCP server that carries private data — or that writes data — must be added to that same exclusion set.
- `Profile.sex`/`documentType`/`documentNumber` (national ID): only `documentNumber` is strictly private (same trust level as `birthDate` — set from `/admin/perfil`, never returned by `getFullProfile()` in `packages/models/src/resume.ts`, `GET /api/resume`, `/cv`, or the MCP tool `get_profile_info`; only reachable via `get_full_profile`'s `documentNumber` key, same personal-integrations-only tool as `Preference`). `sex` and `documentType`, at the owner's explicit request, are **not** treated as restricted — they're in the same public whitelist as `hobbies`/`languages` in `getFullProfile()`/`get_profile_info`, so they're available to `GET /api/resume` and (since `get_profile_info` is a normal, non-excluded tool) the public chat, if a visitor asks. Nothing in `apps/web/src/app/page.tsx` renders them, by choice, not by a security filter — that's the only thing keeping them off the home page's own UI. Worth knowing if that public-chat reachability ever feels wrong in practice — it's a one-line fix (drop them from those two whitelists) if so.
- `DocumentItem` (new collection, `/admin/documentos`) replaces the old `Profile.resumeUrl` field: personal documents as links (Drive, etc.) — `label`, `url`, `kind` (`identidad` | `hoja_vida` | `otro`), `language` (only meaningful for `hoja_vida`), `isPublic` (default **false**), `isPrimary` (default **false**, only meaningful for `hoja_vida` — the API (`apps/web/src/app/api/admin/documents/{route,[id]/route}.ts`) enforces at most one primary `hoja_vida` at a time by unsetting it on every other one whenever a save sets it true). Only `kind:"hoja_vida"` + `isPublic:true` entries are ever public — that's what the home page's "Ver CV" button(s) now query (sorted `isPrimary` first), rendering one `ResumeLink` per match: the primary one (or the only one) is labeled plain "Ver CV", any others get their `language` as a suffix. `getFullProfile()`/`get_profile_info` expose the same set as `resumes: [{label, url, language, isPrimary}]`. Everything else (cédula, a vehicle permit, ...) defaults private and only ever appears via `get_full_profile`'s `documents` key (unfiltered — every `DocumentItem`, public or not, `isPrimary` included). `GET /api/admin/documents` redundantly checks `requireAdmin()` even though `middleware.ts` already gates it, given what it can list. `ResumeLink.tsx` runs every `href` through `lib/drive.ts`'s `toDriveDirectDownloadUrl()` before rendering: a Google Drive "share" link (`.../file/d/ID/view`) opens Drive's HTML viewer, not a download — confirmed with curl (`Content-Type: text/html`, no `Content-Disposition`) — while Drive's `uc?export=download&id=ID` endpoint for the same file does return `Content-Disposition: attachment`, also curl-verified. Non-Drive URLs pass through untouched. Only applied to the home page's click-to-download button — the raw `url` is still what MCP tools/API return, since an LLM or automation wants the canonical link, not a forced download.
- `/admin/documentos` renders as **two independent sections** on one page, not one flat table — "Hojas de vida" (fixed `kind:"hoja_vida"`, plus the "Ver mi CV generado en HTML ↗" link that used to live on `/admin/perfil`) and "Documentos" (`kind` is a real field there, limited to `identidad`/`otro` — `hoja_vida` isn't offered as an option, so a document can't be miscategorized from the wrong section). Both are the same generic `AdminCrudPage` component pointed at the same `resource="documents"`, distinguished only by two new optional props added to it: `fixedValues` (merged into every create/update payload, not shown as a form field — how the "Hojas de vida" section forces `kind:"hoja_vida"` without exposing that field) and `filter` (client-side predicate on the fetched list — how each section only ever shows its own subset). `/admin/perfil` no longer references documents/CV at all; that's fully `/admin/documentos`'s territory now.
- `Blog` (title, description, url, source, relevance 1-10, tags, publishedDate, `reviewed`) is a curated reading list — external articles relevant to the owner's professional growth, not posts he writes. An n8n automation calls the MCP tool `create_blog` roughly every 3 days to register newly-discovered articles; new entries always land with `reviewed:false`. The owner triages them from `/admin/blogs` (mark reviewed, edit, delete). `get_blogs` (the read tool, safe for the public chat) only ever returns `reviewed:true` entries — the same "curation gate" pattern as `Comment.isApproved`/`Reference.isPublished`. `create_blog` is the MCP server's only write tool and is in `PUBLIC_CHAT_EXCLUDED_TOOLS` — a visitor must never be able to create content by asking the chat.
- PostHog (`posthog-js`) adds traffic analytics on top of the existing Mongo-based `AnalyticsEvent`/`computePortfolioStats` system — deliberately additive, not a replacement: the domain-specific counters (top projects by `viewCount`, chat FAQ aggregation) stay exactly as they were, PostHog just adds what wasn't hand-built (time-series traffic, device/referrer breakdown, autocapture of clicks). Scoped to "analytics only" at the owner's explicit choice — `disable_session_recording: true` in `lib/posthog-client.ts`, no visitor screen recording. Pageviews are captured manually (`components/analytics/PostHogPageView.tsx`, on pathname change) rather than via PostHog's own `capture_pageview`, because Next's App Router doesn't trigger a real page load on client-side navigation; `/admin/*` is excluded from what gets sent, same rule `AnalyticsTracker.tsx` already follows for the Mongo pageviews, so "visits" reflects real visitors, not the owner managing content. Fully optional and safe by default: with no `NEXT_PUBLIC_POSTHOG_KEY` set, `initPostHog()` no-ops silently — nothing breaks locally or if the owner never creates a PostHog account.
- `GET /api/resume` is a public, unauthenticated endpoint that returns the entire public profile (profile, experience, education, skills, projects, services, references, gallery) as one JSON payload. `/cv` reads from it too.
- `/cv` is a printable résumé page: on-screen it carries the site's Modo Voz identity, but resolves to clean black-on-white typography under `print:` classes / `@media print` — "download" is the browser's native print-to-PDF via `window.print()`, not a server-rendered PDF (no extra dependency, works on Vercel serverless without a headless-browser function). A `resume_download` analytics event fires on click.
- The contact form (`ContactForm`, `POST /api/contact`, opened via a modal from the home page's email button) sends an email via Resend (`RESEND_API_KEY`, optional — the route fails honestly with a 503 instead of claiming success when unset; delivered `to` is `CONTACT_TO_EMAIL` if set, else `Profile.email` — needed because Resend's sandbox mode only delivers to the account owner's own address) and, best-effort (non-blocking, errors only logged), a Telegram notification to the owner via `sendTelegramNotification` (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, optional). CallMeBot was tried first for WhatsApp notifications and dropped — its public bot was at capacity. Both notification channels are independent and optional; this supplements, not replaces, the existing direct `wa.me` button.
- Public write/compute-costing endpoints carry a lightweight in-memory per-IP rate limit (`apps/web/src/lib/rate-limit.ts`, `checkRateLimit`/`getClientIp`, keyed by `x-forwarded-for`): `/api/chat` 15 req/60s, `/api/transcribe` 15 req/60s, `/api/contact` 3 req/10min, `/api/comments` 5 req/10min. Each returns `429` + a `Retry-After` header and a Spanish error message when exceeded. Deliberately in-memory (no Redis) — appropriate for current traffic, and Vercel's serverless instance recycling makes this best-effort rather than a hard guarantee, which is an accepted tradeoff, not a gap to fix. Live-verified: 6th rapid request to `/api/comments` returned `429` with `Retry-After: 590`.
- MCP tool arguments that reach a MongoDB `$regex` (`get_projects`/`technology`, `get_experience`/`technology`, `get_gallery`/`tag`, `get_blogs`/`tag`) are escaped via `apps/mcp-server/src/lib/escapeRegex.ts` before `new RegExp(...)` is built — without it, a visitor-supplied pattern with catastrophic backtracking (ReDoS) could hang the process, which matters more here than on serverless since `apps/mcp-server` is a persistent Render process shared by every request. Live-verified: a catastrophic-backtracking pattern as `technology` now returns instantly (treated as a literal string, 0 matches) instead of hanging.

## Brand Commitments

**The core, durable brand commitment — stated directly by the owner, not inferred:** the portfolio should feel different from a standard portfolio by reading as an AI chat/assistant experience (not just having a chat subpage), minimalist, icon-led, image-carrying, and dynamic/full of real movement. This surfaced explicitly after two prior visual identities were both built and shipped without ever surfacing it — the owner had wanted this from the start but it only came out once they said "no me gustaron los que me diste... yo desde un inicio quería... un portafolio que se pareciera a un chat de IA." Any future redesign proposal must treat this as the pinned brief, not one option among several, unless the owner explicitly changes it.

A secondary, structural correction the owner gave on the same brief: the conversational/chat framing must stay contained to a greeting moment and the real `/chat` page — every other section (projects, experience, services, skills, hobbies, gallery, comments, contact/map) needs its own fully visible card or grid, never nested inside a chat bubble. This is a scanability requirement, not a taste preference: a recruiter or client skimming the page must be able to find any section without reading through a simulated conversation first.

This project has now shipped four visual identities, each explicitly replaced rather than iterated on: "Mission Control" (instrument-panel/console, rejected as too safe/generic), "El Circuito" (PCB/circuit-board world, green-accented — the owner liked green during that round specifically), "El Panel de Salidas" (split-flap departures board, amber-accented — requested for more impact/movement, but still didn't surface the chat-shaped-portfolio brief and was itself later rejected: "no me gustaron los que me diste"), and the current "Modo Voz" (AI-voice-assistant world, lilac/coral-accented), which is the first of the four the owner picked directly from concrete comps rather than through the skill's dice-rolled process, and the first one confirmed against the actual pinned brief above. Earlier per-round color preferences (green, then amber) belonged to those worlds' own material logic and are superseded, not standing requirements — don't assume either back in for a future world; ask.

## Evidence on Hand

Real profile content is now loaded (name, headline, bio, at least one project). Future work should continue using realistic content consistent with the existing Mongoose schemas, and must not fabricate testimonials, press, or metrics beyond what those schemas define.

## Product Principles

1. Every factual claim the AI or the page states about the owner must trace back to real data from the database — never invented.
2. The portfolio must read as credible to two different evaluators (recruiter and freelance client) at once — same content, no mode switch, dual appeal.
3. The admin dashboard is a private operating tool: clarity and speed over expression.
4. The public site and chat are an experience surface for the owner's professional story: the work leads, the interface recedes.

## Accessibility & Inclusion

No product-specific requirement beyond baseline web accessibility. This redesign explicitly requires a working light mode and dark mode, both with sufficient contrast.
